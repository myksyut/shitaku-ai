# ADR-0008 定例シリーズをチームの持ち物にする

## ステータス

Accepted

ADR-0004（RLSベースの認可）を改訂し、ADR-0005（1エージェント複数定例）を置き換える。

## 経緯

すべてのデータが1人のユーザーの持ち物になっている。定例MTGの準備は複数人の作業なのに、ほかの参加者は前回の決定事項もアクションアイテムも見られない。個人向けのAIエージェントでも「前回の議事録とSlackからアジェンダを作る」ことはできるため、Shitaku.ai の差別化は「チームで共有する会議の記憶」に置く。

現状の作りでは共有を足せない。

- 定例MTGは「同期したユーザーごとに1行」で、Google の iCalUID を持っていない。
- 同期結果が空だと、そのユーザーの定例とトランスクリプトがすべて消える。
- アジェンダ生成は service role で動いていて、RLS が効いていない。
- エージェントは複数の定例をまとめられるので、定例ごとに参加者が違うと誰に見せるか決められない。

## 決定事項

| 項目 | 内容 |
|---|---|
| **決定** | Google カレンダーの繰り返し予定1つを「シリーズ」とし、それを持ち主の単位にする。エージェントと定例MTGは `series` に統合する。参加者は作成者のカレンダーの招待客から自動で決まる |
| **なぜ今か** | 個人向けエージェントとの差別化が必要。データが少ない検証段階のうちに持ち主の単位を変える |
| **なぜこれか** | 招待の操作が要らない。「会議に呼ばれた人がその会議の記憶を見られる」は個人向けエージェントでは実現しにくい |
| **既知の不確実性** | iCalUID が参加者全員のカレンダーで一致するか。本番 Auth でメールアドレスでのサインアップを無効にしているか |
| **撤回基準** | 招待客と Shitaku のアカウントのメールが一致しない例が多く、参加者が自動で入れないと分かった場合 |

### 認可の原則

- 参加者の定義は `public.my_series_roles()` の1か所だけ。RLS とアプリ層の権限チェックの両方がこれを使う（二層防御は維持する）。
- 参加者の判定は Google で確認済みのメール（`auth.identities`）だけを使う。
- カレンダー由来のデータ（シリーズの作成、招待客、回）は `SeriesCalendarMirror` だけが service role で書く。認証済み API でのそれ以外の service role の利用は禁止のまま。
- 資格情報は個人のもので、シリーズからは複合外部キーで作成者の連携だけを参照する。

詳細は [設計書](../design/team-owned-meeting-series.md)。

## 根拠

### 検討した選択肢

1. **エージェントを残し、その下に複数のシリーズを持たせる**
   - デメリット: シリーズごとに参加者が違うとき、エージェント単位のデータの公開範囲を決められない
2. **ワークスペースを作り、メンバーを招待する**
   - デメリット: 招待の手間が増え、汎用ツールと同じ体験になる
3. **シリーズ単位で、招待客から参加者を導出する（採用）**
   - メリット: 設定ゼロで共有される。参加者の定義が1か所に収まる
   - デメリット: Google グループや別名アドレスで招待された人は一致しない

## 影響

- 旧テーブルは `legacy` スキーマに移す。中身は新しいシリーズへ自動ではコピーしない（非公開データを勝手に共有しないため）。
- `/agents`、`/agendas`、`/knowledge`、`/transcripts`、`/calendar/sync` などの API は `/series` 配下に置き換える。
- 参加者はアジェンダの生成と議事録の追加ができない。生成は作成者だけが行う。
